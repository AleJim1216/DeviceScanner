# ScanE agent notes

Expo SDK 57 / React Native 0.86 / React 19. Read https://docs.expo.dev/versions/v57.0.0/ before changing mobile code.

## Product

Local capture coach. The phone captures or uploads device photos. A signed-in phone and the web dashboard share one library (assigned + unassigned). FastAPI on port 8000 names the view, groups chassis, and returns usable / retake / needs_review plus issue codes. Rules come from Capture_Coach `PHOTO_GUIDE.md`, `CHALLENGE.md`, and `RULES_AND_JUDGING.md`.

Required views: `front`, `rear_ports`, `label`. Missing views are per device group. A bad photo of a present view is a retake, not missing.

## Mobile

Session is `mobile/src/profile.js` via `expo-file-system` `device-profile.json`. Do not add an AsyncStorage package. Storage `headerRight` also opens Profile.
- Camera: no top `ActionBar`. Profile is a person-outline overlay (`circleUpload`, safe-area top-right). Do not put Profile in a camera ActionBar; the shutter stays centered. All camera actions sit in the bottom bar with the shutter and Front/Rear/Label chips: Upload circle (`Ionicons` `cloud-upload-outline`) and Storage circle (`images-outline`) left of shutter; session circle (`albums-outline`) and Analyze circle (`search`) on the right. The session circle opens Storage filtered to `currentCameraSet()`. The counter is session photos (`shotsInSet`), not all of Storage. Empty session: Take a photo first. No Practice sets or Clear on camera. Clear is Storage/Photos **Delete all**. `@expo/vector-icons` is a direct `mobile/` dependency (Expo SDK 57 / Expo Go).
- Shutter does not navigate to Analysis. Camera photos persist via `appendCaptured` and stay on Camera. Each camera session mints one set number (`nextSetNumber`) via `mobile/src/cameraSession.js` (`cameraSetNumber` / `currentCameraSet` / `clearCameraSession`). All shutters in that session share that `groupId`. Not all camera photos go to `groupId` 1.
- Upload still saves `groupId` null and opens Storage (route name still Photos, header title Storage). Camera → Storage (Upload and Storage circles) passes `filter: "all"` so a leftover Analysis set filter cannot stick when Photos is already mounted. The session circle passes `filter: currentCameraSet()`. `nextScreen(camera)` is Camera; library still Photos.
- Camera **Analyze** shows Alert: This session vs Storage vs Cancel. This session = persisted shots in the current camera session set, then `clearCameraSession` so the next shutter starts a new set. One photo in the session is unassigned (`removeFromSets`) and analyzed with scope `{ type: "single", shotIds }`. Two or more stay the set (`{ type: "session", setNumber }`). Storage = all persisted shots with a set (`assignedGroupId != null`). Empty session: Take a photo first. Empty storage sets: Group photos into a set in Storage first.
- Unassigned photos are never analyzed from Storage. The exception is Camera **This session** with one photo. AnalysisScreen on focus `loadPersistedShots` then `scopedShots(scope)`. Scope is `{ type: "session", setNumber }`, `{ type: "single", shotIds }`, or `{ type: "storage" }`. Helpers: `assignedShots`, `shotsInSet`, `scopedShots` in `mobile/src/grouping.js`. Storage `canAnalyze` = at least one assigned photo. `clearPersisted` also `clearCameraSession`. `fetchSets`/`analyzeSet` remain in `mobile/src/api.js` but are not called from Camera.
- Display previews stay the stored originals. Analyze resizes an upload copy only (max side 960, JPEG quality ~0.75, `expo-image-manipulator`) and base64-posts JSON to `/analyze/payload`. `analyzeShots` encodes those resized uploads in parallel (`Promise.all`). Unchanged shots (same id + uri) reuse the last `/analyze/payload` photo rows on the phone. Only new or changed shots are posted, unless any shot has no `group_id` (then the whole already-resized batch is sent so Gemini can still group). Storage **Delete all** and selected **Delete** drop that cache. Analyze cache persists in `device-shots/analyze.json`.
- After sign-in, analyze, and Storage grouping/delete, call `mobile/src/dashboardSync.js` so the shared library stays in sync. Skip the push when there is no session token.
- Photos: `SetFilterBar` is a Modal dropdown with a scrollable option list (**All** / **Unassigned** / **Set N**), not chips. `filterItems` / `filterLabel` live in `mobile/src/grouping.js`. Group related actions with `ActionBar` / `ActionGroup`. `ActionBar` uses `justifyContent: flex-start` and `alignItems: stretch`; full groups are `width: 100%` so buttons fill each row with no empty strip on the right. Toolbar: **Select all** (toggles **Deselect** for visible photos) is a full-width `ActionGroup` (same width as **Add to set**). **Create Set** + **Remove from set** share one full row evenly (`flex: 1`). **Add to set** stays its own full row. **Delete** + **Delete all** share one full row evenly. **Add to set** is enabled when at least one photo is selected and at least one numbered set exists; otherwise grey. One set: label **Add to Set {n}**, tap assigns via `assignSet`. Two or more: label **Add to set ▾**, tap opens a Modal dropdown (same chrome as SetFilterBar: fade, ink backdrop, scrollable list, maxHeight 240) listing **Set 1**, **Set 2**, … only (no All, no Unassigned). After add: selection clears, filter stays, no toast/navigation. Already-assigned photos can be moved; choosing the current set is a no-op for those shots. Helpers: `canAddToSet` and `addToSetLabel` in `mobile/src/grouping.js`. Create Set still mints/reuses a set number. Remove from set still unassigns. Filter dropdown still only filters. **Delete all** clears persisted shots after confirm. Multi-select is a teal 3px frame, wash, and check mark. Photos **Analyze** uses assigned-only storage scope; disable/alert if nothing is grouped. Do not analyze unassigned photos.
- Analysis: on focus `loadPersistedShots` then `scopedShots`. `PhotoDetails` shows Set N from the shot’s `groupId`, not an invented server group. The green checklist (Current set / `styles.checklist`) renders only when `analysisReady` and there is more than one photo. A one-photo analysis that is still unassigned shows **Add to set** above **Back to camera**; skip it and the shot stays unassigned. Existing Storage sets drive that button: none mints `nextSetNumber`, one assigns immediately (**Add to Set N**), two or more opens a Modal (same chrome as Storage Add to set, menu above the button) listing **Set N** plus **New set**. Do not add "Tap a photo to open it in the roller." Analysis filter `includeUnassigned={false}`. Roller physics unchanged. Show the roller and photos immediately; do not wait on a full-screen spinner. Below the images, a details card shows the exact copy "Analysis in Progress" (with a small spinner) until that photo has a status, plus Set N when assigned. Do not show issue codes or "No defect code". After status: status badge + Set N, then a View heading (`viewBlock`) and view name, then separate **Problem** and **Solution** surface blocks (`problemBlock` / `solutionBlock`) when `reason` / `guidance` are present. `displayPhotos` / `photoForShot` bind copy by shot cache key (`id|uri`), not `result.photos` index. Carousel item keys use `shot.id` / preview URI, not `photo.image_id`. Cached photos (same id + uri) show their last Usable / Retake / Needs review immediately. A failed analyze must not replace the whole screen. Photos stay. The existing unreachable sentence can appear under the photos with Try again. The page `ScrollView` is vertical only (`directionalLockEnabled`). The green checklist starts collapsed and toggles on tap. **Back to camera** stays pinned at the bottom. The roller shows only the filtered photos. Shared `mobile/src/SetBadge.js` + `theme.setColors` appear on the Photos/Storage grid. The Analysis roller has no SetBadge (Set N is on PhotoDetails). Holding the center photo for `HOLD_MS` (1s) navigates to Photos (`GroupingScreen`, header title Storage), the same Storage page Camera opens. Storage opens filtered to that photo’s set (`storageFilterFromShot` in `mobile/src/grouping.js`), not the Analysis dropdown. An unassigned photo opens Unassigned. Do not restore an in-screen PhotoGrid overlay. Storage keeps Select all, Create Set, Remove from set, Add to set, Delete, Delete all, Analyze, Back to camera, and SetFilterBar with Unassigned.
- Theme: `mobile/src/theme.js`. Do not revert to beige/black bars.
- Roller: JS-driven `Animated` + `PanResponder` in AnalysisScreen. Layout math in `mobile/src/carouselLayout.js`. Fixed 3/4 frame, wrap, 2D scale only. `HOLD_MS` (1s) hold navigates to Photos/Storage; do not open an in-screen PhotoGrid. `PanResponder` claims only horizontal moves (`dx` > `dy`) and rejects termination so the page cannot steal a swipe. Hold uses `onTouchStart` with 8px slop so the page can scroll vertically. `analysis-carousel-planner` owns further gesture plans.
- `assignUploadViews` repeats the selected chip as a hint. The server classifies the real view.
- Metro `/model` → `127.0.0.1:8000` in `mobile/metro.config.js`. Eduroam can block phone-to-PC LAN, so `mobile/src/api.js` still tries LAN Metro (`10.245.114.154:8081`) first, then the current Expo host, then `TUNNEL_ORIGIN`. Health probes abort after `HEALTH_MS` (4000). If 8081 is dead, the phone moves on. If a probe gets an HTTP status (including 502), that Metro is treated as reachable for the next try so Analysis is not stuck waiting on a dead port. A down uvicorn on port 8000 makes Metro `/model/health` return 502; hanging LAN probes never reach Gemini and leave Analysis on "Analysis in Progress". Do not say analyze avoids the tunnel. The Expo tunnel stays.
- Do not add `console.error` for health/analyze calls, including a failed analyze. Failed probes use `console.log`; Expo paints `console.error` as a red `fetch failed` banner. A 503 from `/analyze/payload` means view naming failed on the live server; do not hop to another Metro or tunnel origin.
- Stay in Expo Go. Do not add a UI kit unless asked.
- After UI changes, verify in the browser or on device, not from a single screenshot.

## API

- Uploads: the phone and dashboard post JSON to `/analyze/payload` (base64 photos). Multipart `/analyze` stays for local checks. `score_payload` quality-gates locally. Known practice photos keep hash / filename / fingerprint views so `check_views` does not call Gemini. Unknown photos use exactly one view backend (`ANALYZE_BACKEND=gemini` default, model `gemini-3.1-flash-lite`). Gemini stays the only view backend on analyze. Do not say we switched to the local forest. The forest still lives in `api/backends/local_view.py` and is not imported while Gemini is active. Do not fall back if the key is missing. Do not trust cycled client chips. If a shot includes `group_id`, keep it; Gemini names the view only. Gemini 3 can return a thought object before the photos[] object. Skip JSON objects that lack photos[] and use the first object that has photos[] (`json.JSONDecoder.raw_decode`). Ignore thought parts and set thinking_level MINIMAL. Retry the Gemini call once still applies. View naming logs "Calling Gemini for N unknown photo(s)", "Gemini request model=... photos=N", "Gemini response chars=N", and "Gemini named N photo(s)". Uncertain views are `needs_review` (`view_uncertain`) and are omitted from that group's `missing_views`. Response includes `groups[]` (one checklist per chassis; numeric client ids label as Set N).
- Shared library: `POST /account/login`, `GET`/`PUT /account/snapshot`, `GET /account/photos/{id}`. First Sign in creates the account. Store files under `data/accounts/`. Both phone and web read/write assigned and unassigned photos. Practice `/sets` is unchanged. `GET /account/photos/{id}` is `FileResponse` `image/jpeg` with `Content-Disposition: inline`. This API already has libraries for `alejj12` (20 photos) and `alejj1216` (25 photos); the dashboard only shows them when signed in as that same phone username.
- View training: `api/augment.py` expands the 34 practice images (geometry, photometry, DEMO-tape recolor) for the isolated forest only. `api/features.py` tape mask is not orange-only. Optional extra photos: `data/extra_views/extra_views.csv` (`filename,observed_view`). Quality gates stay on the unaugmented 34. Gemini context lives in `api/backends/gemini_context.py` and is examples-only, not an allowlist. `label` is any identification label (nameplate, serial/asset sticker, barcode plate, DEMO tape, or similar), not orange DEMO tape only. Prefer `label` when the photo is mainly that plate/sticker. The six Capture_Coach exemplars are JPEG-encoded at startup and sent at 512px / quality 60. Local quality measure still uses 960. Same model: `gemini-3.1-flash-lite`.
- Practice sets: use `photo_sets.csv` intended views, then the quality models. `/analyze/set` stays on the server. `fetchSets`/`analyzeSet` remain in `mobile/src/api.js` but are not called from Camera.
- Status: clear defect → retake; rear ports unclear or ambiguous brightness → needs_review; else usable.
- After changing `api/` or retraining, restart uvicorn on port 8000.
- Verify with `python -m api.check_api`, `python -m api.check_views`, and `python -m api.check_account`. Mobile: `node mobile/src/check_profile.js` plus the existing screen/cache checks. `python -m api.train` expands hundreds of local view rows and takes a few minutes.
- A forest guess of `label` is not forced `view_uncertain` just because `orange_frac` is low. Tape is one kind of label.

(`.login-welcome`), then username, password, Sign in, and the phone-credentials hint exactly "Use the same username and password as Profile on the phone." Use the same theme tokens as `mobile/src/theme.js`. Shoelace 2 (CDN) is themed to those tokens. Do not revert to beige/black bars.
- Upload only. Do not add a camera or shutter on the web dashboard.
- Sign in with the same phone username. Libraries already on this API: `alejj12` (20 photos) and `alejj1216` (25 photos). A different username is a different library.
- Storage chrome: chips + filter + live photo count (`N photo` / `N photos`) + Refresh + Upload on one row, then ActionBar groups + Analyze on the next. Refresh calls `pullLibrary` (GET `/account/snapshot`). GET `/account/snapshot` 401 signs the dashboard out (clear session, empty shots) and shows "Sign in again with the same username as the phone." Do not keep a stale session that renders an empty grid with "All photos are in a set". Empty library (zero shots) copy is `No photos on {username} yet. Sign in on the phone with this username, then tap Sync now on Profile.` "All photos are in a set" is only `unassignedCopy` when photos exist and none are unassigned. Storage tiles (`.cell`): `aspect-ratio: 3 / 4`, `min-height: 220px`, photo as `background-image` and `<img>` (`object-fit: cover`) so the cell cannot collapse to zero height. Photos use CSS Grid. Filter / create / add / remove / delete stay. Analyze posts `/analyze/payload`. Analysis: checklist + filter share a row, then `.analysis-body` is a 3fr/1fr grid — roller on the left (`#roller-stage` in `.analysis-rail`), PhotoDetails on the right (`#analysis-details`). The details column scrolls internally (`overflow-y: auto`); the page should not grow from a long card. Roller height uses leftover `.analysis-body` height (`leftoverStageH`), not 520/50vh. Roller math is copied from `mobile/src/carouselLayout.js`; do not invent a different roller. SPIN / HOLD_MS / wrap / 2D scale unchanged. Phone hold still opens Storage; web hold still opens the in-page grid. Dashboard PhotoDetails matches the Expo AnalysisScreen info card. Do not show issue codes or "No defect code". Until a photo has a status, the card shows the exact copy "Analysis in Progress" (with a small spinner) plus Set N when assigned. After status: status badge + Set N, then a View heading (`view-block` / `view-kicker`) and view name, then a **Problem** surface (`problem-block`) for `reason` and a **Solution** surface (`solution-block`) for `guidance` when those fields are present. Phone PhotoDetails stays below the roller in a vertical ScrollView; do not move it beside the roller.
